# 🧵 Многопоточность: Worker Threads vs линейный цикл

Упражнение на `worker_threads`: одна и та же задача решается в одном потоке
и параллельно, после чего сравнивается время. Задача — массив чисел от 1 до
300 000; нужно посчитать, сколько из них делится на 3 без остатка.

Ожидаемый ответ — `100000`, его дают оба подхода. Интересен не результат,
а разница во времени.

## 📁 Структура проекта

```
5_worker_threads/
├── linear.js     # линейный подсчёт одним циклом
├── parallel.js   # нарезка массива и запуск воркеров
└── worker.js     # что делает один поток: считает свой кусок
```

## 🚀 Запуск

```bash
# линейный подход
node 5_worker_threads/linear.js

# многопоточный: число кусков = число ядер (os.cpus().length)
node 5_worker_threads/parallel.js

# многопоточный: своё число кусков
node 5_worker_threads/parallel.js 4
```

Пример вывода:

```bash
$ node 5_worker_threads/parallel.js 4
Многопоточный подход
Ядер (кусков): 4
Размеры кусков: 75000, 75000, 75000, 75000
Делятся на 3 без остатка: 100000
Время подсчёта: 45.0594 мс
```

## ⚙️ Как это работает

**Линейный вариант.** Массив создаётся один раз, а `performance.now()`
вызывается до и после цикла — в замер попадает только подсчёт, без
подготовки данных.

**Параллельный вариант:**

1. `splitArray` (`parallel.js`) делит массив на `N` частей. Остаток от
   деления распределяется по первым кускам, чтобы сумма длин совпадала
   с исходной.
2. На каждый кусок создаётся `new Worker(...)`, кусок передаётся в
   `workerData`.
3. `worker.js` получает свой кусок, считает в обычном цикле и отправляет
   число обратно через `parentPort.postMessage`.
4. `Promise.all` ждёт все ответы, `reduce` складывает их в итог.

## 📊 Замеры

Среднее по 5 прогонам, Node.js v26.13.0, AMD Ryzen 7 4800H
(8 ядер / 16 потоков, `os.cpus().length === 16`).

| Подход                | Кусков | Среднее, мс | Мин, мс | Макс, мс |
|-----------------------|--------|-------------|---------|----------|
| Линейный цикл         | —      | **3.52**    | 2.96    | 3.80     |
| Worker Threads        | 1      | 52.81       | 49.01   | 56.57    |
| Worker Threads        | 2      | 45.49       | 38.49   | 49.64    |
| Worker Threads        | 4      | 45.43       | 44.38   | 47.43    |
| Worker Threads        | 16     | 71.08       | 66.94   | 76.05    |

## 🔍 Выводы

1. **Многопоточный вариант медленнее в 13–20 раз.** Потоки работают
   корректно, но выигрыша нет — накладные расходы больше полезной работы.
2. **Полезной работы слишком мало.** Весь подсчёт занимает ~3.5 мс, то есть
   на 4 куска приходится меньше 1 мс счёта в каждом. Старт одного воркера
   (создание изолята V8, загрузка модуля) стоит миллисекунды.
3. **Увеличение числа потоков не помогает.** 1 воркер — 52.8 мс, 2 — 45.5 мс,
   4 — 45.4 мс. Время почти не зависит от числа кусков, потому что оно
   определяется фиксированной обвязкой, а не счётом.
4. **16 воркеров дороже, чем 4.** Больше изолятов, больше копий данных,
   больше сообщений — на 45 мс счёта это уже заметно.
5. **`workerData` — это копия, а не ссылка.** Кусок массива клонируется
   через structured clone при каждом запуске воркера. Суммарный объём
   копируемых чисел одинаков при любом числе кусков, поэтому эта часть
   времени тоже не уменьшается.
6. **Разброс между прогонами большой** (до ±10 мс). Одиночное измерение
   здесь ничего не доказывает — нужны серии и среднее.

## 💡 Что сделало бы многопоточность быстрее

- **Больше работы на элемент.** Если вместо `% 3` считать что-то тяжёлое,
  доля полезного счёта вырастет и параллелизм начнёт окупаться.
- **`SharedArrayBuffer` вместо копирования.** Данные разделяются между
  потоками, `postMessage` передаёт только индексы границ.
- **Пул постоянных воркеров.** Создавать воркеры один раз, а задачи
  раздавать через `worker.postMessage` / `parentPort.on('message')`.
  Тогда плата за старт платится один раз на всю программу.

## 🧠 Используемые концепции

- **`worker_threads`** — настоящие потоки внутри одного процесса.
- **`workerData`** — стартовые данные воркера (копируются).
- **`parentPort.postMessage`** — отправка результата в главный поток.
- **Structured clone** — неявное копирование данных между потоками.
- **`performance.now()`** — высокоточный замер времени.
- **`Promise.all`** — ожидание всех воркеров параллельно.
